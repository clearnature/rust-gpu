> 日期: 2026-08-22

> 硬件: AMD RX 9060 XT (gfx1200, RDNA4, 32CU, 16GB GDDR6)

---

## 一、项目概述

t0-gpu 是一个零依赖的裸金属 GPU 编译器 + 推理引擎，用纯 Rust 编写，直接通过 KFD/dev/kfd 与 AMD GPU 通信，完全绕过 HIP/ROCm 用户态库。

**核心能力**：
- 从 IR 直接生成 GFX1100/GFX1200 ISA 机器码（不经过 LLVM）
- 手工构建 AMD HSA ELF Code Object
- KFD 裸金属 AQL dispatch（~2μs 延迟 vs HIP 的 10-50μs）
- BF16 WMMA GEMM、FlashAttention、INT4 量化、RMSNorm 等算子

## 三、关键架构

### 编译管线

```
.t0 文本 → Parser → T0 IR → TypeCheck → Semantic Lower
  → T0Kernel (虚拟寄存器指令)
  → SSA 提升 → 13 个优化 Pass → SSA 寄存器分配
  → Wait 计数优化 → Delay ALU 插入
  → 物理寄存器指令 → 二进制发射 → ELF Code Object
```

### K6 Persistent Kernel 模式

```
persistent_loop:
  atomicAdd(counter, 1)  → tile_idx（仅 lane 0 执行）
  readfirstlane(tile_idx) → 广播到所有 lane
  if tile_idx >= total_tiles → exit
  分解 tile_idx → (tile_row, tile_col)
  加载 A/B 数据 → WMMA 累加
  store 结果到 output
  s_branch persistent_loop
```

**关键约束**：
- MES v2 固件 bug：≥4 workgroup → GPU hang（需 1-2 WG）
- SaveExec/RestoreExec 保护 atomicAdd 的 exec mask
- VGPR 指针必须每迭代从 SGPR 重载（寄存器分配器跨回边复用）
- `skip_optimize=true` 禁用 SSA 优化（domtree 不支持 back-edge）

### 文件结构

```
src/
├── kfd/mod.rs              — KFD 运行时（内存分配、AQL dispatch、信号等待）
├── rdna3_asm.rs            — GFX1100/GFX1200 ISA 编码器
├── rdna3_code_object.rs    — ELF Code Object 生成器
├── ignis/gpu_context.rs    — GPU 运行时上下文（GpuRuntime）
└── t0/
    ├── ir.rs               — IR 定义（Op、VReg、SReg、Target）
    ├── compile.rs           — T0Kernel 编译管线
    ├── asm_emitter.rs       — 汇编文本发射器
    ├── ssa_regalloc.rs      — SSA 寄存器分配器
    ├── regalloc.rs          — 非 SSA 寄存器分配器
    ├── tile_ir.rs           — Tile GEMM 编译器（lower_gemm、K6 persistent）
    ├── opt_passes.rs        — SSA 优化 Pass
    ├── block_dsl.rs         — BlockDSL 前端
    └── gpu_tests.rs         — GPU 集成测试
```

## 四、已知问题与解决方案

### 4.1 Dispatch timing 不可靠

**现象**：所有 benchmark 的 TFLOPS 数字不可信（4096³ 显示 2545 TFLOPS，实际应 ~85 TFLOPS）。

**根因**：`GpuRuntime::dispatch()` (ignis/gpu_context.rs:264) 调用 `queue.submit()` + `queue.wait_idle()`。`submit` 写 AQL packet 到 ring buffer 并更新 write_ptr，`wait_idle` 轮询 read_ptr 直到追上 write_ptr。但 read_ptr 在 GPU 处理完 packet 后才更新，而 kernel 可能在 warmup 后立即退出（SGPR counter 问题），导致 `wait_idle` 瞬间返回。

**解决方案**：
1. 修复 persistent loop 的 SGPR counter（见 4.2）
2. 或改用 `AqlQueue::dispatch_signal` + completion signal 等待
3. 或在 `wait_idle` 后添加 PCIe readback drain 确保 GPU writes 可见

### 4.2 Persistent loop 只运行 2 次

**现象**：counter=8（4 waves × 2 iterations），不论矩阵大小。

**可能原因**：
- SSA 优化可能修改了 SGPR loop counter 的逻辑（`skip_optimize` 未设置）
- SGPR 寄存器分配冲突（persistent_iter_s 和 persistent_threshold_s 共用同一 SGPR）
- `SAddU32` 在 GFX1200 上设置 SCC (carry flag)，干扰后续 `s_cmp_ge_u32`

**待验证**：检查汇编中 SGPR 编号是否冲突，或重新启用 `skip_optimize=true`。

### 4.3 acc_swap=true 不累加

**现象**：K-loop 结束后累加器值为零，store phase 写零。

**根因**：`emit_lds_read_and_wmma_swap` 的 acc_swap 逻辑在 persistent 模式下不正确 — K-loop 不保存最终行的累加器到 LDS，store phase 的 LDS swap 读到 stale 数据。

**解决方案**：当前用 `acc_swap=false`（VGPR=157，1 wave/SIMD）。需要修复 acc_swap 的 LDS 保存逻辑。

### 4.4 VGPR 压力

**当前**：241 VGPRs（acc_swap=false + SSA regalloc 变更后）。超过 128 阈值。

**目标**：≤128 VGPRs → 2 waves/SIMD。

**路径**：
- 修复 acc_swap=true（157→104 VGPRs）
- 或减小 tile_m（128→64）减少累加器数量
- 或修复 SSA regalloc 的 reuse detection 减少过度分配

## 五、调度模型参考

来自 `/data/rtl-sdr/docs/` 和 `/data/rtl-sdr/swmmac/`：

```
XDL 管线 = 16 cycles (4-pass × 4 cycles)
VGPR 读端口 = ~7 cycles
VGPR 写端口 = ~3 cycles
有效管线 = 26 cycles

IPC = chain_count / 26
理论峰值 = 64 SIMD × 32768 ops × 2780 MHz = 5830 TOPs (INT4)
实测峰值 = 4368 TOPs (74.9% 理论, K6 wrap counter)
```

**关键约束**：
- 128 VGPR 阈值：≤128 → 2 waves/SIMD，>128 → 1 wave/SIMD
- Silent Drop：EXEC ≠ 0xFFFFFFFF → HWXDL 静默丢弃 VGPR 写回
- 三路数据总线：LDS(A) + Texture(B) + VGPR(ACC) 独立并行
- 外积引擎：A 列广播，B 行隔离
