通用算法思想（可移植到任意 GPU）

    1. 软件流水线 + 多阶段异步（核心价值）

    DeepGEMM 的 mainloop 设计非常精炼：

     1 for each k-tile:
     2     TMA prefetch k+2 tile → SMEM staging buffer
     3     wgmma compute current tile from SMEM
     4     commit/wait barriers between stages

    这个 TMA prefetch → compute → commit 的交错模式在任何 GPU 上都有对应物：
     - AMD RDNA/CDNA: global_load_dwordx4 + s_waitcnt + v_mfma
     - 旧 NVIDIA (SM80): cp.async + mma.sync

    2. Swizzled SMEM 布局

    DeepGEMM 对 SMEM 布局的 swizzle 模式非常讲究（16B/32B/64B/128B），目的是消除 bank conflict。这个思想完全通用：
     - Swizzle 的本质是 (addr XOR offset) % num_banks 的均匀分布
     - AMD 共享内存同样有 bank conflict 问题，同样的 swizzle 模式适用
3. M 维分组 GEMM（MoE 专用）

     1 # DeepGEMM 的 MoE 分组策略
     2 m_grouped_fp8_gemm_nt_contiguous  # 推理 prefill：token 按 expert 拼接
     3 m_grouped_fp8_gemm_nt_masked      # 推理 decode：CUDA graph 兼容的 masked 版本

    这个 "只 group M 维，N/K 固定" 的设计是 MoE 场景的通用最优策略，不依赖任何硬件。

    4. Block 调度器的 Swizzle 策略

    scheduler/gemm.cuh 中的 get_swizzled_block_idx：

     1 // 将 block_idx 映射到 (m_block_idx, n_block_idx)，使相邻 block 在 L2 cache 中重叠
     2 const auto group_idx = block_idx / num_blocks_per_group;
     3 auto first_block_idx = group_idx * kNum1DBlocksPerGroup;
     4 // ... swizzle for better L2 usages

    这是 2D block tiling 的 L2 locality 优化，在任何 GPU 上都有效。CUTLASS 2.x/3.x 也有类似设计。
5. Mega MoE 的计算-通信重叠调度

    scheduler/mega_moe.cuh 的核心思路：

     1 L1 warmup waves (all Linear1 tasks) →
     2 交替调度 L1/L2 tasks，保证：
     3   - L1 产出被 L2 消费前已完成
     4   - NVLink dispatch/combine 与 tensor core 计算重叠

    这个 producer-consumer 流水线 模式是纯算法层面的：
     - 通信层可以是 NVLink、PCIe、InfiniBand
     - 计算层可以是任何 MMA 指令
     - Ring buffer + barrier 同步可以用任何 GPU 的 atomic/fence 实现

    6. MQA Scoring Kernel 的算法设计

     1 # 每个 token i 对所有 token j 计算 logit
     2 out[i,j] = sum_heads(relu(q[i] @ kv[j]) * weights[i])

    这个 weighted ReLU MQA 的分块计算策略（按 seq_len 分 tile，每 tile 内做 head 维 reduction）完全通用。

    7. JIT 编译 + shape-specific 优化

    DeepGEMM 的 JIT 系统将 BLOCK_M, BLOCK_N, BLOCK_K, kNumStages 等作为编译期常量，生成针对特定 shape 的 kernel。这个思路在任何平台上都适用——Triton 就是这么做的。

    8. FP8 per-channel scaling 的通用处理

    虽然 SM90 用 FP32 SF、SM100 用 UE8M0 SF，但 per-128-channel scaling 的算法本身是通用的——只需适配缩放因子的存储格式。

    总结

    DeepGEMM 的真正价值不在于用了什么 SM90/SM100 指令，而在于它展示了一个极简但高效的 GEMM kernel 应该长什么样：精确的 swizzle、清晰的 stage 流水线、L2-aware 的 block 调度、以及 MoE 场景下的分组与融合策略。这些算法思想移植到
    AMD CDNA/RDNA 或旧 NVIDIA SM80 上，框架需要重写，但设计模式可以直接复用。

    最高价值的 3 个交叉点

    1. `14-scheduler-architecture.md` × DeepGEMM 的 swizzle 调度器

    t0-gpu 的 5 层调度架构在 Level 2（指令调度）有软件流水线，但 Level 3（模板调度）的 tile 选择靠 CostModel 穷举。DeepGEMM 的 get_swizzled_block_idx 展示了如何在 Level 3 用 L2 locality 感知的 swizzle 分配
    block——这比纯穷举高效。

    2. `05-ilp-scheduling-analysis.md` × DeepGEMM 的多 stage pipeline

    DeepGEMM 的 mainloop 是 kNumStages=3~5 的 producer-consumer ring buffer，用 full_barrier/empty_barrier 控制流。t0-gpu 的 Phase D 已有 Pingpong 调度，但只做了 2 stage。DeepGEMM 的实现展示了如何扩展到 N stage 并处理 TMA 的
    arrive_and_expect_tx 延迟计数。

    3. `08-ignis-framework.md` × DeepGEMM 的 MoE/MQA kernel

    ignis 有 BF16 GEMM、OCPA attention、SiLU 等单 kernel，但缺 MoE 支持。DeepGEMM 的 m_grouped_fp8_gemm_nt_contiguous（M-grouped 分组）和 fp8_mqa_logits（MQA scoring）是 ignis 下一步最需要补的 kernel 类型。算法可直接移植——底层
    MMA 指令换成 AMD WMMA/MFMA 即可。

 DeepGEMM 对 t0-gpu 虚拟内存设计的参考价值

    1. TMA 描述符 → AMD 上的等价抽象

    DeepGEMM 的 TMA 描述符本质上是一个预编程的 DMA 元数据：

     1 // DeepGEMM: CPU 端编程一次
     2 cute::TmaDescriptor tensor_map_a = make_tma_descriptor(gmem_a, ...);
     3 
     4 // Kernel 内动态替换地址（K-grouped GEMM 的关键技巧）
     5 tensormap.replace.tile.global_address.shared::cta.b1024.b64(tensor_map_a, new_addr);

    在 AMD KFD 上，没有 TMA 等价物，但可以实现类似的 预编程 DMA 描述符：

      1 // t0-gpu 可以设计的等价抽象
      2 struct DmaDescriptor {
      3     src_va: u64,           // GPU VA
      4     dst_smem_offset: u16,  // LDS 偏移
      5     size: u32,
      6     stride: u32,
      7     swizzle: SwizzleMode,  // bank conflict 消除
      8 }
      9 
     10 impl DmaDescriptor {
     11     fn replace_address(&mut self, new_va: u64) { self.src_va = new_va; }
     12 }

    这比每条 global_load_dwordx4 手动计算地址高效得多。

    2. Mega MoE 对称内存 → KFD 多设备映射

    DeepGEMM 的 Mega MoE 用 PyTorch 的 symmetric memory 做 NVLink P2P 通信：

     1 buffer = deep_gemm.get_symm_buffer_for_mega_moe(group, num_experts, ...)
     2 # buffer 内部: 每个 rank 的 VA 指向同一物理内存，通过 NVLink 可见
 t0-gpu 的 KFD 已支持这个模式（10-memory-model-comparison.md）：

     1 // KFD 的多设备映射 = DeepGEMM 对称内存的 AMD 等价物
     2 ioctl(MAP_MEMORY_TO_GPU, MapMemoryArgs {
     3     handle: alloc_handle,
     4     device_ids_array_ptr: &gpu_ids,  // 多个 GPU ID
     5     n_devices: num_gpus,
     6     // 输出: 每个 GPU 的 gpu_vm_addr
     7 });

    差距：KFD 走 PCIe（32 GB/s），NVLink 走 900 GB/s。但算法模式完全相同。

    3. JIT 缓存的虚拟文件系统

    DeepGEMM 的 JIT 缓存（$HOME/.deep_gemm/）按 hash 缓存编译后的 kernel：

     1 hash = sha256(source + compiler_flags + arch)
     2 cache_dir/hash.cubin

    t0-gpu 的 15-universal-runtime-framework.md 设计了类似的 compiler/code_object/，但没设计缓存层。可以参考 DeepGEMM 的 csrc/jit/cache.hpp 和 csrc/jit/include_parser.hpp（跟踪 header 依赖做 cache invalidation）。

    5. 最值得借鉴的 3 点

     1. 地址热替换模式：DeepGEMM 的 tensormap.replace.tile.global_address 让同一个 kernel 处理不同 GEMM 分片而无需重新编译。t0-gpu 可以在 AQL packet 的 kernarg 段设计类似的轻量级地址切换。

     2. 对称内存 + barrier 跨设备同步：DeepGEMM 的 comm/barrier.cuh 用 atomic increment + phase-based wait 实现跨 rank 同步。t0-gpu 的 KFD 有 AMDGPU_GEM_OP_WAIT_IDLE_VALUE 可以做类似的事。

     3. 三层分配器的优先级：docs 中 BumpAllocator / BuddyAllocator / PoolAllocator 的分层设计和 DeepGEMM 的实际使用模式一致——推理场景用 Bump（单次 dispatch），训练场景用 Pool（buffer 复用），通用场景用 Buddy。

    t0-gpu 已有的 LDS 交换实现

    1. ds_swizzle XOR 转置（最精华的部分）

     1 // rdna3_asm.rs — butterfly_transpose_16x16()
     2 // 4 级 butterfly：XOR(1) → XOR(2) → XOR(4) → XOR(24)
     3 // 每级：ds_swizzle + v_cndmask 跨 VGPR 路由
     4 // 结果：16×16 bf16 矩阵原地转置，零 barrier

    这在 DeepGEMM 里不需要——WGMMA 直接处理转置布局（SS_TN 中 T 表示转置 B）。但对 RDNA4 WMMA 来说是必需的，因为 WMMA 要求特定的 A/B 布局。

    2. ds_swizzle 数据交换 vs v_permlanex16

     1 // 方案 A: ds_swizzle (使用 LDS crossbar)
     2 self.ds_swizzle(dest, src, 0x401F);  // SWAP16
     3 self.wait_lgkmcnt(0);                // 必须等！
     4 
     5 // 方案 B: v_permlanex16 (纯 VALU，不碰 LDS)
     6 self.permlanex16(dest, src);          // dest[lane] = src[lane XOR 16]
     7 // 无需 wait！下一个 cycle 即可用

    t0-gpu 同时实现了两种，方案 B 更优（不占用 LDS crossbar，可与并发的 ds_read 重叠）。

    3. lds_load_transposed_tile（从 LDS 读转置块）

     1 // 从 XOR-swizzled LDS 读 16×16 转置矩阵
     2 // 地址计算：row_base + (col_byte ^ ((row & 7) << 4))
     3 // 当前实现有局限：无法动态计算 XOR 偏移，用了 ds_load_u16 的固定 offset

    这个函数目前注释中标注了问题——col_byte ^ mask 不是编译时常量，需要运行时 XOR。当前的简化版假设无 swizzle。

    ---

    DeepGEMM 对 t0-gpu LDS 设计的启示

    1. 多 stage ring buffer 模式（最高价值）

    DeepGEMM 的核心不是单次 LDS 读写，而是 N stage 的 producer-consumer 流水线：

     1 // SMEM 布局：stage 0, 1, 2 交替使用
     2 // Stage i 的生命周期：
     3 //   TMA warp: empty_wait → TMA load → full_arrive
     4 //   Math warp: full_wait → compute → empty_arrive

    t0-gpu 可以用 LDS 实现同样的模式：

      1 // t0-gpu 多 stage LDS pipeline 设计
      2 struct LdsStage {
      3     a_buf: [u8; BLOCK_M * BLOCK_K],  // FP8 A tile
      4     b_buf: [u8; BLOCK_N * BLOCK_K],  // FP8 B tile
      5     full_barrier: u32,                // s_barrier ID
      6     empty_barrier: u32,
      7 }
      8 
      9 // Warp 0 (DMA warp): global_load → VGPR → ds_write → s_barrier_signal
     10 // Warp 1..N (Math warp): s_barrier_wait → ds_read → v_wmma → s_barrier_signal

    关键差异：AMD 没有 TMA 的 arrive_and_expect_tx（字节数通知），需要用 s_barrier_signal 的到达计数来模拟。

    2. WGMMA 的 "零寄存器读取" 无法复制

    DeepGEMM 最大的性能优势是 WGMMA 直接从 SMEM 读操作数——math warp 的寄存器只存累加器。AMD WMMA 必须：

     1 ds_read_b128 → VGPR → v_wmma  (多一跳，占用 VGPR 带宽)

    这意味着 AMD 的 LDS stage 可以比 NVIDIA 窄（不需要 SMEM 存完整 tile），但 VGPR 压力更大。t0-gpu 的 reg_transpose_c_to_ab 和 butterfly_transpose_16x16 正是在弥补这个差距——用 ds_swizzle 在寄存器内完成转置，避免额外的 LDS
    读写。

    3. 真正缺的是：LDS double-buffer prefetch

    t0-gpu 当前的 GEMM kernel 是单 buffer 的——load 一块、计算一块、再 load 下一块。DeepGEMM 的多 stage 模式让 load 和计算完全重叠。在 RDNA4 上：

      1 // 需要实现的模式：
      2 loop {
      3     // Stage (iter % 3): DMA warp 写入
      4     global_load → VGPR → ds_write(lds_stage[next])
      5     s_barrier_signal(full_barrier[next])
      6     
      7     // Stage ((iter-1) % 3): Math warp 读取
      8     s_barrier_wait(full_barrier[prev])
      9     ds_read(lds_stage[prev]) → VGPR
     10     v_wmma
     11     s_barrier_signal(empty_barrier[prev])
     12     
     13     // Stage ((iter-2) % 3): DMA warp 复用
     14     s_barrier_wait(empty_barrier[prev_prev])
     15 }

    这正是 t0-gpu docs/plan/14-scheduler-architecture.md 中 Level 2 的 "软件流水" 部分，但目前只实现了 2 stage Pingpong。DeepGEMM 展示了 3~5 stage 如何处理——关键是 phase 位翻转避免 ABA 问题。
